# AI_RULES.md

Development standards for this repo. `AGENTS.md`, `CLAUDE.md` and `GEMINI.md` all point here.

## What this project is

A client-side Minecraft dye and stained-glass optimizer. It takes a player's dye and
stained-glass inventory and runs an integer optimization to decide which dyes to craft
and how much glass to make. There is no backend, no account and no network-dependent
feature: the solver runs in the browser and the build is static.

Read `CONTEXT.md` before naming anything. Read the ADRs in `docs/adr/` that cover the
area you're working in.

## Tooling

**bun** is the package manager and script runner. Use `bun run <script>` and `bun x`,
never npm/npx.

| script           | purpose                                                       |
| ---------------- | ------------------------------------------------------------- |
| `bun run dev`    | Vite dev server                                               |
| `bun run test`   | Vitest, run once (`server` = node, `client` = browser)        |
| `bun run check`  | `svelte-kit sync` + strict `svelte-check`                     |
| `bun run lint`   | prettier + eslint                                             |
| `bun run format` | prettier write                                                |
| `bun run build`  | static production build (`adapter-static`, fully prerendered) |

The build is prerendered (`src/routes/+layout.ts`), so `hooks.server.ts` only runs at
build time. Paraglide resolves the locale from the URL (`/` = en, `/es/…` = es).
Don't add anything that needs a request-time server: no server routes, no `+page.server.ts`,
no cookie- or header-based logic.

## Structure

- `src/lib/data/` holds typed plain-data objects: `colors.ts` (the 16 Minecraft colors and
  their swatches), `recipes.ts` (the dye-mixing recipes plus a `RECIPE_DATA_VERSION`, each
  recipe citing its source), and `samples.ts` (editable sample inventories).
- `src/lib/optimizer/` is the UI-independent engine: model building, lexicographic
  solving, validation and bottleneck analysis. It takes its recipe set and options
  **explicitly** as arguments. Persisted UI state is only one caller. It never imports
  from `$lib/components`, `$lib/state`, Paraglide or Svelte.
- `src/lib/state/` holds shared UI state as `.svelte.ts` rune classes. Anything that
  persists goes through `runed`'s `PersistedState`.
- `src/lib/components/<feature>/` holds hand-written components (`inventory/`, `results/`,
  `plan/`, …). Cross-feature compositions go in `src/lib/components/common/`.
- `src/lib/components/ui/` is generated by shadcn-svelte. Change it only through the CLI
  (`bun x shadcn-svelte@latest add …`). If a primitive gets a project variant, re-add it
  by diffing, not by overwriting.
- `src/routes/` pages only put components together. They don't carry visual utilities
  (`text-*`, `bg-*`, `border*`, `rounded*`, `shadow*`, `font-*`) on bare elements.
  Layout utilities on a wrapper are fine.
- Component files are `kebab-case.svelte`. Props are a documented `interface Props`
  destructured with `let { … }: Props = $props()`.

## Optimizer rules

- Recipes are data. Adding or changing a Minecraft recipe must never require touching the
  optimizer.
- Quantities are integers end to end. No floating-point approximation of dye, glass or
  recipe executions. Validate every solver result against the inventory (conservation,
  no negative dye, existing glass preserved) before showing it.
- Results must be deterministic when several optima tie.
- The regression sample in `samples.ts` and its expected optimum (K = 9, T\* = 152,
  spread = 5) is **locked behavior**. It can change only with a `RECIPE_DATA_VERSION`
  bump and a note explaining which verified recipe forced the change.
- Never claim a unique bottleneck unless it's proven. Say "one smallest resource
  increase…".

## UI and UX conventions

- **shadcn-svelte**, `luma` style, `taupe` base. Fonts: Outfit Variable (`font-heading`) for
  headings and figures, Inter Variable for body. Numeric columns use `tabular-nums`.
- **Primitives first.** Pick UI in this order: (1) an installed primitive and its variants,
  (2) a composition in `common/` or a feature folder, (3) a new variant on the primitive
  when a style repeats, (4) hand-written markup only when nothing covers it. Steppers
  (+/−, set to 0) use `ButtonGroup`. Numeric fields use `InputGroup` or `Field`. Tabular
  data uses `Table`. Tags use `Badge`. Alerts use `Alert`. Empty or loading states use
  `Empty`/`Spinner`. Charts use `Chart` + `layerchart`. Expandable detail opens in a
  `Dialog` (on mobile, `Drawer` is acceptable if it shares the same content component).
  No raw `<input>`, `<select>`, `<button>` or `<table>`. A long `class` string at a call
  site means a variant is missing.
- **Colour comes only from theme tokens** (`bg-background`, `text-muted-foreground`,
  `border-border`, …). Never hard-code hex/oklch or use raw palette classes like
  `bg-red-500`. **Only exception:** the 16 Minecraft swatches in `src/lib/data/colors.ts`,
  which are domain data. Apply them through one swatch component, never ad hoc. Dark
  mode must keep working.
- **Accessibility:** every interactive target is at least 44px. Focus must be visible.
  Icon-only buttons need `aria-label`. Decorative icons get `aria-hidden="true"`. Colour is
  never the only way a swatch is identified; always show the colour name next to it.
- **Layout by width, not device:** stack below `md` and use columns from `md` up.
  `useIsMobile` (`$lib/hooks/is-mobile.svelte.ts`) is the 768px breakpoint.
- Notifications use `toast` from `svelte-sonner`. Never use `alert()`/`confirm()`; use
  `AlertDialog`.

## Language and formatting

- Every piece of interface copy lives in Paraglide messages (`messages/en.json`,
  `messages/es.json`). `en` is the base locale. Add both locales in the same change. Never
  leave a hard-coded user-facing string in a component.
- Use `CONTEXT.md`'s vocabulary in both languages. Keep **dye units**, **recipe
  executions**, **plain glass** and **stained-glass blocks** visibly distinct.
- Format numbers only with `Intl.NumberFormat` and the active Paraglide locale
  (`getLocale()`), never a hard-coded separator or locale.
- Every user-facing item count also shows its Minecraft equivalent in stacks of 64
  ("152 blocks · 2 stacks + 24"). Both come from one shared formatter, and the stack
  phrase is a pluralized Paraglide message, not string concatenation.

## Persistence

- localStorage keys are versioned (`dye-optimizer:v1:<name>`). A breaking shape change
  bumps the version instead of migrating silently.
- JSON import is validated against a schema: non-negative integers, known colors, and a
  `recipeDataVersion`. Anything invalid is rejected with an explanation, never partially
  applied.

## Documentation

- `CONTEXT.md` is the domain glossary. Use its terms, and don't drift to the synonyms it
  lists under _Avoid_. If you need a term that isn't there, add it rather than inventing
  one ad hoc.
- `docs/adr/NNNN-kebab-title.md` records architectural decisions (solver choice, objective
  design, persistence shape…). If a change contradicts an ADR, say so explicitly and
  write a superseding ADR instead of silently overriding it.
- Recipe data cites its source. Nothing about Minecraft behavior may be inferred.

## Before finishing

Run `bun run test`, `bun run check`, `bun run lint` and `bun run build`. All must pass.
Don't commit, push or add deployment configuration unless asked.

## Svelte MCP

The Svelte MCP server has the Svelte 5 and SvelteKit docs.

#### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

#### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

#### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

#### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.
